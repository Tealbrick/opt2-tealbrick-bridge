## 0.2.11 — app hold status and caller context; scope sources in the status report (bridge#26, C331 D8); caps `app_hold_status`, `app_call_context` (C367 P3, P4; spec 0.1.77)

- **`tb.hold_status` for an app caller (BRIDGE §8.3 v0.1.77, cap `app_hold_status`).** On the companion path the standard op is routed when the presented grant's `wf` lists it (`runGate`; MANIFEST M-CP-3 mints it there). `gate()` already skips the CRUD ceiling and the workflow step for it (I4), so the bridge adds the `wf` check for app callers only: not listed → 403 `not_in_workflow`. Target gate (PK-D6): the op goes to a target only when its last reported `sdkVersion` (the status push, `ctx.health`) is at least `APP_HOLD_STATUS_MIN_SDK` (`app-calls.ts`, "0.1.41": a reservation until the miniapp-sdk that ships SDK-API §4.7 is released); lower, malformed or never reported → `not_in_workflow` and the target is not called. Agent calls are unchanged. The app's answer is passed through as it is: an unknown or not-owned hold is the app's `404 hold_not_found` (errata 1), and after the approved repeat the receipt status is `run` (errata 2, the app's rule).
- **Caller context (BRIDGE §8.5, cap `app_call_context`).** A companion `CallEnvelope.context` is accepted. After the grant is selected and before any hook the bridge checks it with the manifest package's `callerContextProblem(<the presented grant's verified prd, else null>, context)`: absent or `{}` adds nothing; a problem is 400 `input_invalid` with `error.details.pointer` (`/context` or `/context/<key>`), the message never repeats a value, nothing is forwarded and no hook runs. The product is never read from the envelope. The keys are copied into the op body `context` before the before-hook chain (like `tb.onBehalfOf`), so hooks and the app see them and the op proof's `ctx` digest covers them: a context changed after signing fails `call_proof_invalid` at the app. The context is informational: the gate, the grant checks and the hooks' authority never read it. A context hook may still add only keys under its own product, so a hook of the caller's own product can overwrite a caller key and no other hook can.
- **Caps.** `StatusReport.bridge.caps` (and re-minted standalone slices) add `app_hold_status` and `app_call_context`, each with a probe in `caps.test.ts`. `DeclaredCap` is now `BridgeCap` (spec 0.1.77 carries every cap).
- **Pins.** `@opt2-tealbrick/spec` 0.1.78 (the C367 errata). `@opt2-tealbrick/manifest` 0.1.32, the release with `callerContextProblem` (the one implementation, L1), in `packages/bridge` and in the relay override `@opt2-tealbrick/relay>@opt2-tealbrick/manifest` (`manifest-one-version.test.ts`). `APP_HOLD_STATUS_MIN_SDK` = miniapp-sdk 0.1.41, the release that ships SDK-API §4.7. `secret_output` stays undeclared: manifest 0.1.32 still refuses `secretOutput` (sdk#51 not merged).
- **Hooks never match standard `tb.*` ops (MANIFEST §16, Rules F2).** `hookMatches` returns false for standard ops and non-agent audiences, so a wildcard hook no longer runs on `tb.holds_pending` / `tb.hold_status` and a hook outage no longer fails them closed (call path and event rule 6). Tests (`hook-standard-and-companion.test.ts`): wildcard deny hook, unlisted declared hook, and companion hook deny / after redaction / `after_failed` (Rules F1).
- **Resolve cache follows the running release (QA-P5-3).** A cached dynamic resolution is dropped when its instance leaves the table or runs another release (manifest digest changed: update, rollback, candidate), so a tool the update reclassified is resolved again at once instead of keeping its old crud/effect for up to 5 min (hooks keyed on `effects` would miss it; the target SDK re-resolves every call, so grants were never at risk).
- **Release (catch-up wave, C373).** `tealbrick-ci.json` `upgradeFrom: ">=0.1.31"`: ostra's stable 0.1.34 and every 0.2.x dev line (qa1) may update to this release; older bridges are untested against the 0.2 data and are not offered it. Core already refuses a lower version (`catalog.ts latestOn`).
- Tests: `packages/bridge/test/c367-app-hold-status-context.test.ts` (B31 and B32, bridge side; mutants: no `wf` rule, caller keys not merged) and the two cap probes.
- Version: 0.2.11, the next free version after bridge#23 (0.2.10); a reservation, assigned at merge (C340/C357).
- **From bridge#26 — scope sources in the status report (C331 D8; spec 0.1.65); the report stays under Core's ack cap.**
- `scope_summary` answers may carry `sources` (the agent's scope instances: type, the app's instance id, label, access). Of the FIRST 20 items, the bridge keeps the well-formed ones (snake type and access; the id is the app's own: `<prefix>_<ULID>` or a lower-case slug, and not a UUID or a lower-case `acct_1nfj…`-style token, so provider ids such as Stripe or Slack ids are dropped), makes labels well formed (a lone surrogate becomes U+FFFD), removes `\p{Cc}`/`\p{Cf}` and cuts them at 60 code points (never half a surrogate pair), and forwards them in `StatusReport.scopeSummaries[].sources`. Malformed items are dropped, never repaired, so fewer than 20 may remain. An answer without `sources` (SDK before 0.1.65) forwards none. A change of sources alone pokes Portal like a label change. Display only. Scope summary labels are cut at 80 code points the same way.
- **The status report stays under 240 KiB** (Core reads 256 KiB; QA: one app could push 443 KB). Over that, the bridge cuts only what apps can grow, from the app that grew most first: the `sources` of that app, then long `attention.reason` texts (to 500 code points), then omitted tools and scope summaries to 50 per app, then those lists whole, then `attention`. Each cut adds one `rejected` marker per app (`kind: bridge_op`, code `report_truncated_sources` | `_attention` | `_tools` | `_scopes`, count = items cut).
- **Report bound follow-ups (QA-BR26D-1..3).** One `rejected` marker per (code, app): a later stage that cuts more of the same kind for the same app adds to its count (omitted tools 10 + 50 = 60; `attention` counts the app once). Two last cuts for reports that stay over the cap with many apps (`roles[]` rows are about 2.5 KiB per app at max size): `connectionsSeen` to the newest 100 (marker `report_truncated_connections`, no `ins`), then the detail of `roles[]` rows app by app (`provider`, `model`, `dataPolicy` become `null`, `policyBasis` is removed; marker `report_truncated_roles`, count = rows reduced); `role`, `ins`, `set`, `policyOk` are required by the spec and stay. `rejected.code` is an open string in spec 0.1.71, so the new codes need no spec change. apps, keys, claims, rejected and `bridge.caps` are still never cut. The relay override stays on spec 0.1.57 as on main; this PR changes no dist pin.


## 0.2.10 — hook target tool, secretOutput ops; cap `hook_tool` (C336 RQ-2, RQ-3; spec 0.1.68, specs#47)

- **Hook target `tool` (BRIDGE §8.2 v0.1.68, cap `hook_tool`).** On all three dynamic call paths (a listed dynamic entry and `<op>_call` over MCP, the relay's dynamic call, a companion call of a dynamic op on the internal listener; all through `CallRouter.route`) every hook request (before, context, after) carries `call.target.tool` = `DynamicResolution.tool`, the app's canonical resolution, with `crud` / `effect` / `holdFamily` from that resolution. Absent for static ops; dynamic search never routes a call. A resolution whose `tool` is not EXACTLY the requested name, or does not match `^[a-z][a-z0-9_]{1,62}$` (a catalog name of at most 48 chars, or a variant the agent requests itself such as `<tool>__first_contact`, at most 63), is refused 403 `dynamic_resolve_failed` (`details.reason: "tool_mismatch"`, not cached) before any hook runs: a case, space or alias variant is never mapped onto a held tool.
- **`secretOutput` ops (MANIFEST M-OP-12, cap `secret_output`).** The op is never listed for agents (`visibleOps`), an agent call is refused 403 `secret_output_app_only` before anything runs, and for an app caller the bridge calls no `after` hook, forwards no idempotency key (the app keeps no row) and returns the result to the calling app only. Logs and status fields carry ids, codes and digests only, as for every call.
- **`requires.bridgeCaps` at registration (C354, QA-C354-2).** The manifest fetch refuses an app whose `requires.bridgeCaps`, or a feature it uses (a `secretOutput` op → `secret_output`), names a cap this build does not declare: rejected kind `manifest`, code `bridge_cap_missing`, the missing cap in the `bridge.rejected` log detail; the app is not routed. A neighbour claim refuses 409 `bridge_cap_missing` with `details.cap`. The needed caps come from manifest `requiredBridgeCaps()` once the pinned API has it, read structurally until then (`caps.ts missingBridgeCap`). Never a version comparison; it only refuses.
- **Caps.** `StatusReport.bridge.caps` (and re-minted standalone slices) add `hook_tool`, with a probe in `caps.test.ts`. `secret_output` is NOT declared yet (C354): this build pins manifest 0.1.30, whose validator refuses a manifest with `secretOutput`; the cap comes with the re-pin to manifest ≥ 0.1.31.
- **Compatibility.** A dynamic engine whose resolved tool names are not canonical (upper case, `-`, longer than 63 characters) or whose `resolve` answers any name other than the one requested is refused from this version on. Requested names of 49–63 chars pass the bridge's input check only after it re-pins a manifest whose `DYNAMIC_CALL_INPUT_SCHEMA` allows them (sdk#51).
- The spec 0.1.68 fields are read structurally (`// spec 0.1.68`): pins stay spec 0.1.57 / manifest 0.1.30 until spec 0.1.68 and manifest 0.1.31 are released. Until the manifest re-pin, this bridge's validator refuses a manifest that declares `secretOutput` (fail closed). Such a manifest lists `requires.bridgeCaps: ["secret_output"]` (C354); Core deploys it only onto a bridge that declares the cap.
- Tests: `packages/bridge/test/c336-hook-tool-secret.test.ts` (B29.hook_target_tool_list / _call / _relay, B29.hook_tool_bypass, 49- and 63-char names equal to the request pass, a differing resolution (also `<requested>__<suffix>`) and 64 chars are refused; the 63-char full MCP path runs after the manifest re-pin (skipped until then: the pinned validator refuses requests over 48 chars), C-SO-1/2 bridge part with positive controls — the not-listed check builds the tool index after the op is in the table, and the `visibleOps` mutant B14 fails it) and `c354-bridge-caps.test.ts` (declared cap registers, missing cap refused, implied `secret_output`) and the `hook_tool` cap probe.
- Version: 0.2.10, the next free version after bridge#27 (0.2.8) and bridge#22 (0.2.9) (C354a); provisional, assigned at merge (C352).

## 0.2.9 — model roles and agent persona (C330(4), C322(3), C320, C312a; spec 0.1.71)

(0.2.8, below, is the patch release of bridge#27; this line was built as "0.2.8" during review and is released as 0.2.9.)

- **Cap** `model_roles` in `StatusReport.bridge.caps` (and in re-minted standalone slices): this build implements all of BRIDGE §15 (probe in `caps.test.ts`). Core sends `agents[].persona` and `modelRoleRequirements[]` only to a bridge that declares it.

- **S11 model-role bindings** (`models.sealed.json`, sealed like S3): `{role, ins?, provider, model, baseUrl?, keyName?, dataPolicy, zdrAttestedAt?, dims?}`, workspace default + per-app override, resolve override → default. The key store also holds owner-named provider keys (label ≤ 60) in their OWN namespace (`pk:<label>`, QA-BRIDGE22-1): an app requirement with the same name never reads a provider key (`GET /tb/v1/keys/<name>` serves only requirement keys) and the page shows the two sections apart; a key store written by a released bridge (0.2.7; bridge#27's 0.2.8 keeps its state code) holds requirement keys only and loads unchanged — tested with a store written by the released code (fixtures/released-0.2.7). One key can serve many roles. A requirement (app) key never satisfies a binding (spec 0.1.69): the binding form offers provider keys only, and a stored binding that names anything else (e.g. an app key) is not served (resolve `role_not_set`, status `set: false`) and shows "key missing" on the page. Any binding or key change bumps `keysRev` once (wakes `/tb/v1/status` long-polls as before); a crash between the two writes is repaired at boot; older volumes load unchanged; KEK rotation reseals the new record.
- **"Keys and models" page** (same origin, ticket, session, CSRF, CSP, no-redirect rules): Provider keys (write-only, "Serves: role (apps)", deleting a key that serves a model asks first and leaves the binding without a key) and Models (one row per `modelRoleRequirements[]` role; providers from the spec catalog filtered by role, local first; base URL required when the provider has no default; `local` only for a §15.3 URL; `zdr` only for zdrOffered providers with the owner's tick, stored as `zdrAttestedAt`; "Automatic" = `local` for a passing URL; embeddings change warning; per-app override). The model label must match `MODEL_ID_PATTERN` and the provider must be a catalog id; anything else is refused. Ticket `roles[]` hints (at most 8, same patterns) pre-fill for display only. No provider test call. The base URL follows the §15.3 transport rule below.
- **App-key names** (QA-BRIDGE22-6): the bridge acts only on config key requirements whose name is an app-key name (spec `EnvName`, `^(?!TB_|RAILWAY_)[A-Z][A-Z0-9_]{1,63}$`); any other name (e.g. `pk:…`) is dropped, so it is never fetched, listed, set or reported as an app key, even when a config lists it.
- **Path errors** (QA-BRIDGE22-2): a malformed percent escape in `/tb/v1/model-roles/<role>` or `/tb/v1/keys/<name>` is `400 bad_request` (spec 0.1.71) right after the caller is authenticated (a bad or missing TB-Assert stays 401), never 500.
- **Resolve** `GET /tb/v1/model-roles/<role>` on the internal listener (instance or service assertion): `paused`, `role_not_declared`, `role_not_set`, `role_policy_too_low` (`details {needed, have}`, no binding field), key unset → `role_not_set`; `ModelRoleFetchResponse`, `Cache-Control: no-store`; values never logged. An instance override is used even when it fails the policy (no fall-back to the default). The §15.3 check (spec follow-up #49 at 5676915, text only, never DNS): input hygiene (`\`, `@`, their look-alikes U+FF20/U+FE6B/U+FF3C, `%40`/`%5C` in any case, whitespace, NUL/DEL and other control characters, `?`, `#` refused anywhere), WHATWG parse, http(s) only; the canonical `url.href` is the only form stored and served (`ModelRoleFetchResponse.baseUrl`); host lower-case, one trailing dot removed, Node's bracketed hex IPv4-mapped form decoded BEFORE the checks. NEVER_LOCAL (169.254/16, fe80::/10, fd00:ec2::254, the Alibaba/Oracle/Azure metadata addresses, 0.0.0.0/8, `::`) and NEVER_LOCAL_HOSTNAMES are never local, even when listed. ## 0.2.7 — app events (C274c/C274d; spec 0.1.57, manifest 0.1.30, conformance 0.1.28)

- **Ingest** `POST /tb/v1/events` on the internal listener (BRIDGE §14.1): instance assertion of the claimed app instance (`htm`, `htu`, `bd`); a companion service → 403; body ≤ 512 KiB, 1..100 items processed in order with one result per item; 429 from the companion-call bucket of the instance; 503 `app_not_claimed` for an instance the config does not list. Per item the §14.1 steps in order (declaration, shape and size, scoped ⇔ `instanceId` + `eligible`, target ⇔ `to`, dedupe of `(app instance, key)` for 7 days, emits and purges alike), with the shared rules of `@opt2-tealbrick/manifest` 0.1.30.
- **Per-agent log** in `node:sqlite` (`<TB_DATA_DIR>/bridge/events.db`; no new npm dependency): ULID ids strictly increasing per bridge (also after a clock step back and a restart), `origin`, the recorded declaration (manifest digest, `visibleWith` op, its scope type), the `eligible` authority, the envelope, ingest time, `held`. Retention per agent: 7 days from ingest or 10 000 rows (oldest by ingest first), `droppedThrough` and a held-row-removed flag answered once as `truncated: true`.
- **Fan-out at write** by MANIFEST §16.2 rules 1–4 (the tools/list rule via `eventVisibleToGrant`, `eligible` with its per-entry authority, never outside it, never to `causedBy`, `to` for target events). **Re-check at delivery** of rules 1, 5 and 6 against the current table and the current serving manifest; pause and G2b waits hold rows, which get new ids (same `origin`, old order) in the same step as the resume or the switch; a rollback drops them. A matching enabled before/after hook strips `summary`.
- **Purges** per agent + instance and for every agent of an instance (delivered or not).
- **MCP**: `tealbrick/events/list`, `tealbrick/events/poll`, `tealbrick/events/stream` on the agent's existing session; `notifications/tealbrick/event` frames on the GET stream with SSE `id:` = event id (no `id:` on other frames), `Last-Event-ID` resume, a second `stream` replaces the subscription and re-sends the backlog; `cursor_invalid` → -32602; paused → `paused: true`. Event reads have their own per-connection rate bucket (20/s, burst 200).
- **Review round 1 (bridge#16):** open event streams are re-authorized (connection active, same `gen` and agent, token not expired) on every config swap and before every flush, and closed at token expiry; a per-app-instance stored-row limit (6 000/min, burst 30 000; 429 / 413 for the whole batch); event-log failures never take the bridge down (corrupt file moved aside, `events` cap only while the log is healthy, ingest 503 / methods -32601 otherwise); counts reset on rollback; drain-aware frame writes; `events/list` skips paused and down instances.
- **Review round 2 (bridge#16):** connection gen and token expiry are per GET stream (a pairing refresh or a Portal rotation closes the old stream and keeps the session and its subscription; a revoke or agent change ends the session); only I/O-class SQLite errors count as unhealthy, with hysteresis for the cap (withdrawn after 5 min, restored after 3 good probes); move-aside only for CORRUPT/NOTADB with a reset point (`truncated` for a cursor below it), any other open failure runs without the log and retries; one drain listener per slow flush.
- **Review round 3 (bridge#16):** the dedupe `keys` table is capped per app instance (100 000, oldest first); the log has a size cap (1 GiB used pages, `TB_EVENTS_MAX_BYTES`) and ingest is refused (503 + Retry-After) when the volume has under 128 MiB free; `events.db`, `-wal` and `-shm` are 0600 and documented as unsealed and part of volume backups; a non-limit ingest failure is logged as `bridge.events.ingest_failed`; `events/poll`, `events/stream` and the live flush fail closed on an expired config (-32000 `config_expired`); ARCHITECTURE section 12 documents WAL on NFS, `synchronous = NORMAL` durability and when a corrupt file is repaired.
- **Cap** `events` in `StatusReport.bridge.caps` (and in re-minted standalone slices), next to `owner_rows`.
- Pins: `@opt2-tealbrick/spec` 0.1.57, `@opt2-tealbrick/manifest` 0.1.30 (also for the relay's validator: a manifest with `events` needs it), conformance 0.1.28, miniapp-sdk 0.1.38 (tests).
