# Tealbrick bridge: architecture

State: verified against the repo on 2026-10-16. Claims cite paths in this repo. Anything not verified is marked UNVERIFIED. For the whole system see the system `ARCHITECTURE.md` and `SYSTEM-OVERVIEW.md`.

## 1. Listeners

- **Public** (`PORT`, default 8080). Max 2000 connections, 50 per client, request timeout 30 s, headers timeout 15 s. HSTS when `TB_PUBLIC_URL` is https. Two host names: the main origin and the keys origin (`TB_KEYS_PUBLIC_URL`, a different host name, startup throws otherwise). The keys origin serves only `GET/POST /keys`, `/healthz`, `/readyz`. On the main origin `/keys` is 404 (or a 503 "key page not configured" page when the keys origin is unset).
- **Internal** (`TB_INTERNAL_PORT`, default 8788). Private network only. Bind: `TB_INTERNAL_HOST` when it is an IP address, else `::` in the deployed form (`127.0.0.1` on own_infra). Advertised host (the `internalUrl` apps get in the claim answer): `TB_INTERNAL_HOST` when it is a NAME (S1; stable across a container recreate; never bound; refused on own_infra), else `RAILWAY_PRIVATE_DOMAIN`, else the bound IP, else the container host name.

Public routes: `/healthz`, `/readyz`, `/mcp` (POST, GET SSE, DELETE), `/.well-known/oauth-protected-resource[/mcp]`, `/.well-known/oauth-authorization-server`, `/oauth/{register,authorize,pair/callback,token,revoke}`, `/agent/connection/revoke`, `/a/<product>/*` (person launch, app UI proxy, WebSocket for UI paths), `/p/<product>/<path>` (declared public routes only, 1 MiB cap), `/admin/v1/*` (answers only in standalone mode), `/_tb/*` (exact static allow-list). `/readyz` is 200 only when identity and a routing table exist. It does not check config age (the platform RUNBOOK says it does: mismatch).

Internal routes: `GET /tb/v1/views/<product>/<rest>` and `GET /tb/v1/views/_ready` (0.2.1, section 11; own key check, not an instance assertion), `POST /tb/v1/claim`, `POST /tb/v1/status` (long-poll up to 60 s), `GET /tb/v1/keys/<name>`, `POST /tb/v1/call` (app to app; 503 with `Retry-After` while draining), `POST /tb/v1/events` (0.2.7, app events ingest, section 12; 503 with `Retry-After` while draining), `GET /metrics` (Prometheus text, no auth, so the private bind matters). Callers prove themselves with an instance assertion (`tb-instance-assert+jwt`, bound to method, path and body, 60 s, one-use `jti`, proofs issued before bridge boot refused for 90 s).

## 2. Enrolment and the Portal link (`packages/bridge/src/portal.ts`, `state.ts`)

- First start needs the one-time `TB_ENROL_CODE` (`tbe_...`, at most 24 hours). The bridge generates its Ed25519 key (K7), posts `/api/v1/bridge/enrol`, and verifies the response's key-set statement against root keys built into the bridge (`manifest.trustedPortalKeys`) BEFORE writing anything. A bad statement refuses enrolment and the refused code digest is saved so restarts do not retry it.
- **`PORTAL_ROOT_CHANNEL` is the build constant `"dev"` (`packages/bridge/src/context.ts`).** The comment says the cutover release must switch it to `"prod"`. Production root keys do not exist yet.
- Every later request to Portal carries `TB-Assert` (`tb-bridge-assert+jwt`, 60 s, bound to method, path and body). Redirects are refused.
- Config pull (`runConfigLoop`): `GET <configPath>?after=<rev>&wait=60`, 75 s per-request timeout, 5 s minimum spacing, error backoff 5 s doubling to 240 s, `Retry-After` clamped 30 to 900 s, 4 MiB cap. `verifyConfig` checks `v`, workspace, subject and audience, strictly increasing `rev`, expiry, and that the signing key is `active` or `pending` in the pinned statement. The table is built off to the side and swapped as one pointer. The last good config is kept in `<TB_DATA_DIR>/bridge/config.jws` and re-verified at boot with only the age check waived.
- **Fail closed:** a config older than its `exp` (12 hours) makes agent and app-to-app calls answer `config_expired`. Person surfaces stay up so the owner can act.
- Status report: after each applied revision (2 s debounce), at least every 5 minutes, retry 15 s to 300 s. Content is names, ids, counts and presence booleans only. Since 0.1.30 it also passes `schemaVersion {app, sdk}`, `minCompatibleCode` and `failure` from the app status through (shape-checked, malformed values dropped). Since 0.1.31 it passes `preUpdateSnapshot` too: `null`, or a ref with well-formed `file`, `sha256`, `createdAt`, `from`, `to` (one bad member drops the whole ref; spec 0.1.39 types the member on AppStatus but not yet on the report entry) and sends an extra health event when they change, so Core's update gate wakes at once.
- Update candidate (since 0.1.33, spec 0.1.51): while Core runs a health-gated update of an app, its `apps[]` entry carries `candidateManifestDigest` + `candidateVersion` (both or neither) next to the serving `manifestDigest`. The table build (and its previous-manifest cache), the manifest retry and the claim accept a manifest whose digest equals either value. The bridge uses the manifest the service serves and reports that digest in `StatusReport.apps[]`; any other digest is `manifest_mismatch` as before.
- App manifests are fetched from `<internalUrl>/tb/v1/manifest` (10 s), must match `manifestDigest`, and a failed app is marked `down` and retried (backoff 2 to 60 s). `internalUrl` must be `http://<name>.railway.internal:<port>`, or, only for entries with `ownInfra: true`, an exact origin in `TB_OWN_INFRA_ORIGINS` (BSD-07). **`TB_OWN_INFRA_ORIGINS` is read once at boot** (`server.ts`, `ownInfraOrigins`): adding or removing an own-infrastructure app means changing the env and restarting the bridge (SIGTERM drains first; in Docker the env is fixed at container create, so the host agent recreates the container). The host agent does this after every change to the app set (S1-0 contract section 5.6).

## 3. Call pipeline (`calls.ts`, `table.ts`)

Order per call: resolve target (dynamic ops resolve through the app, with CRUD and effect ceilings and a hold family for outward and money), select grant, validate input, derive or require the idempotency key, `gate()`, `requireListedHooks`, before hooks, context hooks, config age, re-gate on the current table, re-check listed hooks, forward, after hooks (only on `ok`). The decision functions live in `@opt2-tealbrick/manifest` (`gate`, `verifyGrant`, `reduceBeforeChain`).

- Hook order is one total order: phase, `order`, product id, hook id, by code unit. Timeout is `min(max(timeoutMs, 100), 2000)` ms. A before or context hook that errors, times out, answers a bad shape or whose app is down: `hook_failed` (fail closed). A context hook may not write outside its own `<product>.` namespace or any `tb.*` key. A failing after hook withholds the output and marks the receipt `after_failed`.
- Hook caller product (0.2.2, spec 0.1.45): the `call` object sent to every hook phase (before, context, after) has `caller.product` when the caller is an app: the product of the calling instance in the bridge's own signed config (`Table.apps`), never from input, a header or a manifest name. It is absent for agents and for an app caller the table cannot map; a policy app then treats the caller as unverified.
- Hook target tool (0.2.8, spec 0.1.68, C336 RQ-2, cap `hook_tool`): for a dynamic call (listed entry, `<op>_call`, relay or companion call of a dynamic op) the `call.target` of every hook phase carries `tool` = the resolution's canonical tool, and `crud` / `effect` / `holdFamily` are that resolution (`effectiveOp`). Absent for static ops. A resolution whose `tool` differs from the requested name or is not `^[a-z][a-z0-9_]{1,47}$` is refused `dynamic_resolve_failed` before any hook (`resolve`, not cached). A policy app (Rules) matches it exactly; the bridge never interprets it.
- `secretOutput` ops (0.2.8, spec 0.1.68, MANIFEST M-OP-12, C336 RQ-3, cap `secret_output`): never listed for agents (`tools.ts visibleOps`), an agent call is refused `secret_output_app_only` at the start of `route`; for an app caller no `after` hook runs (the result goes to the caller only), no idempotency key is forwarded, and nothing of the result is logged (the call line carries ids, codes and the input digest only, as for every call). Read structurally (`tools.ts isSecretOutputOp`) until the spec pin carries the field.
- GRANT-PRD (0.2.3, spec 0.1.46, manifest 0.1.23): a companion grant may carry `prd`, the product of the calling instance. `gate()` shape-checks it: a well-formed `prd` passes, a malformed one is `grant_invalid` and nothing runs. The hook rule stays "the table decides": `caller.product` is the instance table's product. When the presented grant also carries a `prd` and it differs from the table's product, the hook request leaves `product` out and the bridge logs `bridge.hooks.caller_product_mismatch` with both product ids (no tokens). With no `prd` the table's product is used as before. The call itself is not refused for the mismatch.
- Tool index (0.2.6, C296; `mcp.ts`, `tools.ts`, `calls.ts`): the per-(config revision, agent) MCP tool index records when it was built, whether it holds dynamic list entries and whether a catalog failed. A stale index still answers at once and ONE background rebuild replaces it: past `dynamicIndexTtlMs` (= the catalog TTL, 5 min) the agent's catalogs are expired and asked again; after `incompleteIndexRetryMs` (30 s) only what is not cached (the failed catalog) is asked again. A refresh that fails keeps the last good entries (`catalogFresh` → `stale`) and marks the index incomplete; a catalog that never answered throws as before. A rebuild that changes the tool set sends `notifications/tools/list_changed` to that agent's sessions; it runs on the agent's next request (no timer), so an idle client hears it when it next asks. A config revision or a scopes change still rebuilds at once.
- Owner rows (0.2.5, spec 0.1.50, C283 A1; `tools.ts`, `scope-summary.ts`): the SDK may admit a scoped op above the Portal grant's `crud` through an owner-set row. `gate()` (manifest 0.1.27) skips `op.crud ⊆ grant.crud` for an op with a `scopeType` and keeps it for an unscoped op; the SDK decides (`scope_denied`) and pause, revoke, expiry and holds are unchanged. The bridge only DISPLAYS: a static scoped op above the grant is listed when the app's `scope_summary` answer names it in `admittedOps` for that agent (the other listing rules come from `opVisibleToGrant` with the grant crud widened), and a dynamic catalog entry marked `admitted: "owner"` is listed (the body of the catalog bridge op carries `agent`; the catalog cache is per agent). `admittedOps` is never part of the StatusReport. The scope summary is asked when the app's `scopesRev` changes, when a pause is lifted, and on demand with an age bound (tools/list older than 30 s; a tools/call of an unlisted static scoped op of a granted app, at most every 5 s per app).
- Capabilities (0.2.5, spec 0.1.54, C292; `caps.ts`): `StatusReport.bridge.caps` lists what this build implements (`owner_rows`). A cap is added with the code it names and never ahead of it; `test/caps.test.ts` keeps a probe per cap. A standalone bridge sets `slice.bridge.caps` in the slices it re-mints.
- Hook proof `bd` (0.2.5, spec 0.1.52, C268 B/c; `proof-caps.ts`): the hook request body is serialised once, hashed and sent as those bytes; the call proof carries `bd` only when the hook app's stored `proofClaims` (its claim, then each status push of the app instance) list `"bd"`. The stored set changes only on a config change of that app's `manifestDigest`, `version`, `candidateManifestDigest` or `candidateVersion` (dropped), a re-claim (the claim's set) and a push whose version or set differs, accepted only when the push reports the version the config names for the app (serving or update candidate) and its assertion `iat` is not older than the last accepted push (a push held back by a network attacker cannot downgrade). A connect failure, timeout or 401 never changes it, and a 401 is not retried without `bd`. Companion service claims and pushes never touch it. In memory only: after a restart there is no `bd` until the app's next push.
- A hold verdict from a before hook becomes the `hv` claim in the op call proof. The first hold is kept; a later refuse wins. The app decides the hold.
- Forward: `POST <internalUrl>/tb/v1/ops/<op>` with grant and `TB-Call` proof (60 s, `gjti`, `in`, `ctx`, optional `hv`). Timeout 30 s, one retry only on a pre-connect error, results capped at 4 MiB. App error codes pass through only if they look like `^[a-z][a-z0-9_]{1,40}$` and are not a bridge verdict code.
- Companion calls: re-entry from inside a hook is `hook_reentry` (409), depth over 3 is `call_depth_exceeded`, app-initiated calls are limited to 120 per minute with burst 30.
- Drain (F57a): on SIGTERM new `tools/call` answer `temporarily_unavailable` with `Retry-After: 2`; in-flight calls get 25 s, then answer `app_unavailable` ("outcome unknown, check before retrying") and are never re-sent. Set `RAILWAY_DEPLOYMENT_DRAINING_SECONDS=30` (Core does).

## 4. Identity, MCP and OAuth

Only K5 agent access tokens (`tb-agent-session+jwt`, 900 s, signed by the bridge key) are accepted at `/mcp`. No person credential is ever accepted. Each request re-checks the current table. Connection methods: **key** (the agent presents a K4-signed assertion, jwt-bearer grant, 60 s, one-use `jti`; every failure answers `connection_unknown`, no oracle) and **pairing** (OAuth authorization code with PKCE S256 and a rotating refresh `tbr_`, 30 days sliding; reuse of an old refresh revokes the chain, reason `refresh_reuse`). DCR is stateless (`client_id` is `tbc_` plus a sealed registration). MCP limits: 16 sessions per connection, 10 requests per second burst 40, 8 concurrent calls per connection, 256 global, body 2 MiB. Tools are named `<product>__<op>`. Skills are served as resources plus a `<product>__tb_skills` fallback tool.

## 5. State on disk (`<TB_DATA_DIR>/bridge/`, dir 0700, files 0600)

Sealed with `TB_KEK` (AES-256-GCM): `identity.sealed.json`, `connections.sealed.json`, `claims.sealed.json`, `jtis.sealed.json`, `keys.sealed.json`, `standalone.sealed.json`, `reports.sealed.json` (persisted revocations kept until Portal has them), `enrol-refused.sealed.json`. Not sealed: `config.jws` (Portal-signed) and `events.db` (0.2.7, the app event log, section 12: every delivery re-checks the signed table, and cached manifests are used only under the digest the config names). Writes are crash-safe (temp file, fsync, rename, directory fsync). Plaintext state from bridges older than 0.1.12 makes boot fail with `state_corrupt`. `TB_KEK_PREVIOUS` reseals every record for one start. In memory only: replay sets, OAuth state, MCP sessions, key-page sessions, rate windows. Never stored: tool inputs or outputs, holds, receipts, app data, person credentials, the enrolment code itself.

## 6. Timers

Event log sweep (60 s: the 7-day age rule for every agent and the dedupe window, 0.2.7), config loop (continuous), status loop (2 s debounce, 5 minutes), manifest retry (1 s tick), standalone re-mint (60 s tick, re-mint when under 6 hours remain), MCP session sweep (10 minutes), OAuth sweep (60 s), key session sweep (60 s), Docker HEALTHCHECK (30 s).

## 7. Image

`packages/bridge-server/Dockerfile`: Node 24 slim pinned by digest, `USER 1000:1000`, `EXPOSE 8080 8788`, no `VOLUME`, HEALTHCHECK on `/healthz`. When the platform starts it as root (`RAILWAY_RUN_UID=0` for a volume) the entry chowns `TB_DATA_DIR` and drops to 1000 before loading state or listening; it refuses to stay root. `bridge-runtime.json` describes ports, health paths, volume, and env sources for Core's deploy recipe.

## 8. Standalone mode

A final Portal-signed config with `standalone` freezes the bridge: it stops pulling, re-mints grants, slices and config with its own key every 6 hours, and exposes four admin operations (pause, resume, revoke a connection, tickets) authenticated by an owner assertion. One way.

## 11. The two roles (0.2.1, LA-1, C232; `views-edge.ts`, `views-route.ts`, `views-shared.ts`)

One image, two roles by `TB_ROLE` (`packages/bridge-server/src/server.ts`, `roleOf`): `bridge` (default) or `views`.

```
viewer → https://<tb-views domain>/v/<product>/<token>[/…]          tb-views (TB_ROLE=views, public, stateless)
       → http://<bridge private host>:8788/tb/v1/views/<product>/<rest>   bridge PRIVATE listener (TB-Views-Key)
       → http://<app private URL>/v/<product>/<rest>                the app's `viewer` public route (unchanged path)
```

- **Views role** (`startViews`). No volume, Portal, enrolment or keys; refuses to start with `TB_ENROL_CODE`, `TB_KEK`, `TB_KEK_PREVIOUS` or `TB_PORTAL_URL` set, or without `TB_VIEWS_UPSTREAM` and `TB_VIEWS_KEY` (messages name variables, never values). Serves `/v/<product>/<rest>`, `/healthz`, `/readyz` (ready = the bridge `_ready` answers; reused 2 s); everything else 404; HEAD and OPTIONS 405. Only the allow-listed request headers go on (`VIEWER_REQUEST_HEADERS`; absent stays absent) plus `TB-Views-Key`. 120 requests per minute per client (first `X-Forwarded-For` hop, else the socket address; over → 429 + Retry-After), 32 in flight (over → 503 + Retry-After), a body over 2 MiB → 502, no answer in 10 s → 504, bridge unreachable → 503 "viewer address not ready". It logs no path and no query (the path carries the viewer token). A process started as root drops to 1000 first.
- **Bridge private route** (`ViewsRoute`, called from `InternalApi`). The key (`TB_VIEWS_KEY`, and during a rotation also `TB_VIEWS_KEY_PREVIOUS` while it is set; each at least 16 characters) is compared in constant time against both; missing, wrong or unset is a 404 identical to an unknown path. Refuses (400) a request with Cookie, Authorization or any `TB-*` besides the key. Routes by product to the instance whose manifest has a `viewer` public route (else 404; app down → 503 retry). Workspace or instance pause from the signed config → 503 `paused`; a config past its 12 h life → 503 `config_expired`. Its own in-flight cap (32) keeps `/mcp` free. Forwards `GET /v/<product>/<rest>` with the allow-listed headers, 2 MiB, 10 s. The answer is shaped by `shapeViewerAnswer` (also used by tb-views): the floor, the dropped headers and the `_d` gate, and the app's value of a floor header replaces the floor's only when the manifest's `viewerFloorOverride` says so (CSP always; `public, max-age=<n>, immutable` Cache-Control only on `/v/<product>/_s/…`, 0.2.2).
- **Both** shape the answer with one function (`shapeViewerAnswer`): `Set-Cookie`, `Access-Control-*`, `X-Frame-Options` dropped; `VIEWER_HEADER_FLOOR` set, the app replacing only `Content-Security-Policy` (all its values kept); for `/v/<product>/_d/…` (also written `%5Fd` or with doubled slashes) the answer needs a safe sandbox over all CSP values, else 502 `viewer_document_unsafe` with no path in the body.
- **Status.** With `TB_VIEWS_PUBLIC_URL` the bridge probes `<views>/readyz` (3 s) before each report and every 60 s, and reports `views {url, ok, lastCheckAt}` (a change of `ok` pokes a report; `lastCheckAt` alone does not). Without it the member is absent.
- **Origins.** The main origin and the keys origin answer 404 for `/v/*`; the private route does not exist on the public listener.

## 12. App events (0.2.7, spec 0.1.57, BRIDGE §14, C274c/C274d; `events.ts`, `internal.ts`, `mcp.ts`)

- Store: `node:sqlite` (built into Node 24, no npm dependency), `<TB_DATA_DIR>/bridge/events.db` (WAL). Tables: `rows` (one row per agent and event: `id` ULID = the cursor, `origin` = the first id, `agent`, app instance `ins`, `product`, `type`, `instance_id` (scoped events), the recorded declaration `digest` + `op` (`visibleWith`) + `scope_type`, the agent's `eligible` `authority`, the envelope JSON, `ingest_at`, `held`), `agents` (`dropped_through`, `held_dropped`), `keys` (dedupe of `(ins, key)` for emits AND purges, 7 days), `manifests` (content-addressed manifests of the releases the config names, so the SERVING manifest stays known while a G2b candidate runs, also after a restart), `meta` (schema version, last issued id). Ids are strictly increasing per bridge: a ULID, or the successor of the last issued id when the clock is behind (also across restarts).
- Ingest `POST /tb/v1/events` (`internal.ts ingestEvents`): instance assertion (`htm`/`htu`/`bd`) of the APP instance (a companion service 403 `no_grant`); body ≤ 512 KiB (413), 1..100 items (400); the companion-call bucket of the instance (120/min, burst 30 → 429 + `Retry-After`); not in the config → 503 `app_not_claimed`; expired config → 503 `config_expired`. Items in order, one transaction, one result each; the §14.1 steps (declaration from the serving manifest, else the candidate's during a G2b attempt; product `tb` and unknown `tb.*` → `event_reserved`; shape and sizes; scoped ⇔ `instanceId` + `eligible`; target ⇔ `to`; `eligible` ≤ 500; dedupe) use the `@opt2-tealbrick/manifest` rules (`eventDecl`, `eventScopeType`, `validateEventPayload`, `eventVisibleToGrant`, the limits). A name the serving manifest lacks while an attempt runs makes the bridge fetch the running app's manifest once and keep it when its digest is the candidate's; a manifest the batch needs and the bridge does not hold → 503 `app_unavailable` (retryable; nothing decided).
- Fan-out at write: candidates = `to` or every agent with a grant to the instance; rule 3 (`causedBy`), agent in the config, rule 2 (`eligible`, per-entry authority), rule 1 (`eventVisibleToGrant` = the tools/list rule with the A1 owner exception). A paused instance's rows, and rows whose op only the candidate has, are stored `held`.
- Delivery (`page`): rows after the cursor in id order; per row rules 1, 5, 6 against the CURRENT table and serving manifest, op from the recorded declaration: scope type differs → drop; instance paused or op missing during an attempt (or serving manifest not known yet) → mark held; failed grant check or op missing without an attempt → drop; an enabled before/after hook that matches the op (`calls.ts eventHookMatches`; a declared hook missing from the config counts, fail closed) → no `summary`.
- Held rows: every table change (`ctx` `table` event, the store's listener runs first, in the same synchronous step as the swap) releases held rows whose reason is gone with NEW ids in old-id order (`origin` kept), and drops held rows whose op is gone after a rollback or whose instance left the config.
- Retention per agent: rows older than 7 days from ingest, then the oldest by ingest beyond 10 000 rows; `dropped_through` = the highest id removed, `held_dropped` = a held row was removed (answered once as `truncated: true`). Applied on insert (row limit), on every poll/stream call and by the 60 s sweep.
- MCP (`mcp.ts`): `tealbrick/events/list|poll|stream` on the existing session; cursor not a ULID → -32602 `data.code: cursor_invalid`; poll `limit` clamped to 1..100 (default 50); agent or workspace paused → `paused: true`, nothing dropped. `stream` sets the session's ONE subscription (a second call replaces it and frames the backlog after its cursor again); frames `notifications/tealbrick/event` with SSE `id:` = event id go only to open GET streams, flushed after each ingest commit, on every table change and on GET open; `Last-Event-ID` on a GET resumes while the session holds its subscription. Event reads have their own per-connection bucket (20/s, burst 200; a POST whose declared length is ≤ 4 KiB is read before the rate check to tell them apart); every other POST keeps the general bucket.
- Limits and failure handling (review rounds 1 and 2): stored recipient rows per app instance are a token bucket of 6 000 per minute, burst 30 000 (`EVENT_FANOUT_LIMIT`); a batch that would exceed it is rolled back whole and answered 429 + `Retry-After` (413 when the batch alone needs more than the burst, so the SDK halves it). Rule 1 is evaluated once per distinct grant shape per item. A failed transaction rolls back and drops the row-count cache. Only SQLite I/O-class errors (FULL, IOERR, CORRUPT, NOTADB, READONLY, CANTOPEN) make the store unhealthy; others fail only their request. Unhealthy → ingest 503 at once; the `events` cap (`caps.ts bridgeCaps`; methods -32601 without it) is withdrawn only after 5 min of continuous unhealth and restored after 3 consecutive good probes (60 s apart); the status report is poked only on those two flips. At open, CORRUPT or NOTADB moves the file to `events.db.corrupt-<ms>` and starts a fresh log with `meta.reset_through_id` (a cursor below it answers `truncated: true`); any other open failure (disk full, permissions, a newer schema after a downgrade) leaves the file untouched and the bridge runs without the log, retrying on the probe. The store's table listener never throws into a config apply.
- Stream authorization (review rounds 1 and 2, S1): a session lives while its connection is active for the same agent and the agent is in the config; a revoke or an agent change ends it at the next table swap or flush. The connection `gen` and token `exp` belong to each GET stream: a stream opened with an older gen (pairing refresh, Portal rotation) or an expired token is closed before any frame, while the session and its subscription stay (the client reopens GET with a current token and Last-Event-ID). Each stream also closes at its own `exp`. Frames wait for `drain` (one listener per slow flush). `events/list` skips paused and down instances as tools/list does.
- Disk, file and durability (review round 3). **Disk guards:** the dedupe `keys` table holds at most 100 000 keys per app instance (`EVENT_KEYS_PER_INSTANCE`; past it the oldest by time go, down to 90 %; every accepted item writes a key, also one with no recipient); the log as a whole stops taking ingest at 1 GiB of used pages (`EVENT_DB_LIMITS.maxBytes`, `TB_EVENTS_MAX_BYTES` overrides) or when the volume has less than 128 MiB free; ingest then answers 503 `app_unavailable` + `Retry-After: 60` (log line `bridge.events.disk_guard` on each change), delivery, retention and the sweep go on. The bridge's identity and config live on the same volume, so the log must never be able to fill it. **File:** `events.db`, `-wal` and `-shm` are mode 0600 (an existing file is tightened at open). The log is NOT sealed like the S-records: event summaries and payload data are plain text in it, and it lives in `<TB_DATA_DIR>/bridge/`, so it is part of any volume or directory backup of that folder (Platform backup scope: include it knowingly, or exclude `events.db*`; losing it only loses undelivered events, agents then get `truncated: true`). **Errors:** a store failure that is not a disk guard or a rate limit is logged as `bridge.events.ingest_failed` (code only) and answered 503. **Config age:** ingest, `events/poll`, `events/stream` and the live flush all fail closed on a config older than its `exp`, like a tool call (poll/stream answer JSON-RPC -32000 `data.code: config_expired`, frames stop until the next config swap); `events/list` lists types only, as tools/list does. **Durability:** SQLite runs in WAL with `synchronous = NORMAL`: a process crash or restart loses nothing that was acknowledged, but an OS crash or power loss can drop the last acknowledged ingest transactions (the SDK outbox has already been told `stored`); this is accepted for 0.2.7 (events wake agents, the data is read through ops). **Filesystems:** WAL needs shared memory and working file locks, so `<TB_DATA_DIR>` must be a local disk: a Railway volume is, an NFS/SMB mount (an own_infra bridge on a NAS) is NOT safe. **Repair:** a CORRUPT/NOTADB file is detected and moved aside only when the log is OPENED (at boot, or by the probe while it is closed); a file that goes corrupt while the bridge runs keeps the log unhealthy (ingest 503, cap withdrawn after 5 min) until the next restart repairs it.
- Cap: `events` in `StatusReport.bridge.caps` (`caps.ts`), tied to all of the above (`test/caps.test.ts` probe; `test/events-store.test.ts`, `test/events-e2e.test.ts`; conformance B-EV-1..18).
